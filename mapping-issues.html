Mappningsissues och Designbeslut

Mappningsissues och Designbeslut

Denna sida dokumenterar öppna designfrågor och fattade beslut för mappningar från svenska RIVTA-tjänstekontrakt (TKBer) till FHIR R4-resurser inom ramen för EHDS-TK. Sidan används som arbetsunderlag under implementationsguidearbetet och uppdateras löpande i takt med att frågor utreds och beslut fattas. Varje issue är kopplat till ett eller flera tjänstekontrakt och beskriver det tekniska problemet, möjliga lösningsalternativ samt aktuellt förslag eller fattat beslut. Öppna frågor kräver vidare utredning eller nationellt samordningsbeslut innan de kan avslutas.

Designbeslut (fattade)

ID TK Beslut Motivering
GENERAL-001 Alla TK RIVTA-tidsstämplar (YYYYMMDDhhmmss, utan tidszon) tolkas som lokal tid i Europe/Stockholm med hänsyn till sommartid. dateTime får explicit offset (+01:00/+02:00). instant-fält (t.ex. Provenance.recorded, DocumentReference.date) anger samma tidpunkt, helst med samma offset-form; Z endast efter korrekt konvertering. Se Tidsstämplar och tidszon. dateTime med klockslag utan tidszon är ogiltigt i FHIR. Att blint lägga till Z på lokal tid ger 1–2 timmars fel. Samma offset-form för dateTime och instant gör data konsekvent.
GENERAL-002 Alla TK OID-till-URI-mappning för typ-OID:n i patientId (PersonIdType.type; root i de TK:er som använder IIType): fasta mappningar 1.2.752.129.2.1.3.1 → personnummer URI, 1.2.752.129.2.1.3.3 → samordningsnummer URI, 1.2.752.129.2.1.4.1 → urn:oid passthrough. Okänt OID behålls som urn:oid. Säkerställer enhetlig och förutsägbar identifieringshantering för svenska nationella identifierare i FHIR.
GENERAL-003 Alla TK Provenance-agenter: två agenter definieras — custodian (vårdgivare/yttre Sparr) och author (vårdenhet/inre Sparr). Gäller alla TK. Tydlig ansvarskedja i Provenance-resursen krävs för spårbarhet och PDL-krav.
GENERAL-004 GetAlertInformation Flag vs AllergyIntolerance: Flag skapas alltid. AllergyIntolerance skapas dessutom om hypersensitivity-blocket anges. Flag.extension[allergyReference] pekar på AllergyIntolerance. Flag täcker alla typer av uppmärksamhetsinformation. AllergyIntolerance skapas kompletterande för allergier, eftersom det är den FHIR-resurs som bär överkänslighetsinformationen och den ingår i EURIDICE resursåtkomst.
GENERAL-005 Alla TK meta.source = källsystemets Endpoint i tjänstekatalogen: https://tjanstekatalogen.inera.se/Endpoint/{hsaId}. Se meta.source. Det tidigare formatet urn:oid:1.2.752.129.2.1.4.1#{hsaId} är inte en giltig OID-URN i FHIR och avvisas vid validering.
GENERAL-006 Alla TK Patienten refereras med både reference och identifier. API:et skapar en SEEHDSPatient-resurs (EU Core Patient) utifrån patientId; birthDate härleds ur personnummer/samordningsnummer och name anges med data-absent-reason om det är okänt. Se Patientreferens. HL7 Europe Core kräver subject.reference. Ersätter det tidigare avsteget med enbart logisk referens, som inte är förenligt med EURIDICE.
GENERAL-007 Alla TK Konformitetsansats. IG:n utlovar att samtidigt (1) bära samma kliniska information som TKB:erna som FHIR-resurser, (2) vara en giltig profilering av EURIDICE (hl7.fhir.eu.health-data-api) genom att profilerna ärver HL7 Europe Core där sådan finns, och (3) följa svenska basprofilernas namngivnings- och slicingkonventioner (SEEHDS…, Id = namn, slicarna personnummer/samordningsnummer/nationelltReservnummer/hsaid). IPS och EPS är inspiration, inte löfte. Krav och strukturer som bara fanns för IPS/EPS-harmonisering har tagits bort: härledd Condition.clinicalStatus = active (GetDiagnosis), krav på Observation.category för tillväxt och mödravård, LOINC-slicen för tillväxtmätningar och EPS-profilen i meta.profile. HSA-id anges med systemet urn:oid:1.2.752.29.4.19. Se Vad IG:n utlovar. Tydliga, verifierbara löften. Följsamhet mot IPS kan inte förenas med EU Core och TKB:ernas innehåll utan härledda värden.
ALERT-003 GetAlertInformation Alignment med HL7 Sweden UMI-IG (SEAlertInformationFlag): SEEHDSFlag inkluderar standard flag-detail-extension (hl7.org) för framtida länk till Observation med kliniska detaljer. flag-detail möjliggör framtida rikning mot Observation när kliniska detaljer finns tillgängliga.
PDL-001 Alla TK approvedForPatient = false → meta.security kod NOPATIENT (v3-ActCode). Standardkod NOPATIENT är närmast semantiskt korrekta för "ej avsedd att visas för patient". Undviker custom extension.
OBS-001 GetObservations ts-strängar: precision ≥ dag → valueDateTime; YYYY/YYYYMM → valueString. time.ts med låg precision: effectiveDateTime + extension[originalText]. Preserverar precisionssemantik utan att tappa strukturering för datumvärden.
OBS-002 GetObservations valueNegation=true → dataAbsentReason.code = "not-detected". Koden signalerar att det kliniska värdet explicit frånkänts/negativt påvisats.
OBS-003 GetObservations ConceptMap ObservationStatusMap.fsh skapad (5 SNOMED CT-koder → FHIR ObservationStatus). Okänd kod → unknown. Nödvändig för att producera giltig Observation.status. Publiceras som del av IG.
OBS-004 GetObservations targetSite[0] → bodySite; targetSite[1..*] → extension[additionalBodySite] (R4-övergångslösning). Bevarar alla anatomiska platser utan informationsförlust. Extension utgår vid R5-migration.
DIAG-001 GetDiagnosis diagnosisBody.chronicDiagnosis → lokal extension Condition.extension[chronicDiagnosis] (ConditionChronicDiagnosis) med valueBoolean. Extensionen utelämnas om fältet saknas i källan. Bevarar källans boolean oförändrad, inklusive explicit false. Alternativet Condition.category valdes bort eftersom kodsystem för "kronisk" saknas och false inte kan uttryckas meningsfullt som kategori.
DIAG-002 GetDiagnosis diagnosisBody.relatedDiagnosis.documentId → standardextension Condition.extension[relatedCondition] (http://hl7.org/fhir/StructureDefinition/condition-related) med logisk referens valueReference.identifier.value = documentId. En extension per relatedDiagnosis; identifier.system sätts lika som Condition.identifier.system på den relaterade diagnosen. HL7-standardextension för samband mellan diagnoser (t.ex. bidiagnos → huvuddiagnos). Logisk referens kräver inte att den relaterade Condition-resursen finns i samma svar. Alternativet Condition.note valdes bort då det inte är maskinläsbart.
DOC-001 GetCareDocumentation Paginering via hasMore stöds inte av IG:n och mappas inte till FHIR. Den behöver hanteras utanför IG:n. FHIR DocumentReference saknar motsvarighet till RIVTA-pagineringen.
DOC-002 GetCareDocumentation Provenance.recorded = header.author.timestamp; när author.timestamp saknas (dvs. author saknas) faller Provenance.recorded tillbaka på header.record.timestamp. Provenance.recorded är 1..1 och record.timestamp är alltid närvarande (1..1).
DOC-003 GetCareDocumentation signature.timestamp mappas till DocumentReference.extension[ext-signature-time] (ext-signature-time) när den finns. När den saknas sätts ingen ersättning. Bevarar signeringstidpunkten utan att hitta på värden när den saknas i källan.
DOC-004 GetCareDocumentation clinicalDocumentNoteText är av typen string. När DocBook används ska fältet innehålla XML, och XML-tecknen måste då entity-kodas (t.ex. &lt;article&gt;). DocBook förs inte över som DocBook till FHIR. DocBook-innehåll transformeras till XHTML i DocumentReference.content.attachment med contentType: text/html; charset=utf-8 (Strategi A, obligatorisk). Det kan dessutom mappas till en Composition enligt SEEHDSCompositionCareDocumentation med en section per DocBook-<section>, kopplad via Provenance.target (Strategi B, valfri, men profilen gäller om den skapas). DocBook i clinicalDocumentNoteText känns igen på entity-kodad XML; DocBook i en bilaga känns igen på multimediaEntry.mediaType (application/docbook+xml). Fritext mappas som text/plain; charset=utf-8. Se DocBook-mappning. DocBook är ett källsystemsformat som FHIR-konsumenter inte kan förväntas rendera. XHTML kan visas direkt och bevarar källans ordning, och Composition ger sektionerna struktur.
AUDIT-001 Auditloggning Egna AuditEvent-profiler som ärver från IHE BALP (paket ihe.iti.balp): SEEHDSAuditEventPatientQuery (sökning och träfflista) och SEEHDSAuditEventPatientRead (innehållshämtning). Den tidigare profilen för GetAccessLogForPatient heter nu SEEHDSAuditEventReadAccessLog och används bara för att läsa loggar. Loggposterna som API:et skapar måste följa IHE:s mönster (mXDE/ATNA) och kunna lämnas ut till patienten. Att skilja på att läsa loggar och att skapa loggar gör profilernas syfte tydligt.
FUNC-001 GetFunctionalStatus PADL-poster kodas som Condition.note med format [typeOfAssessment]: assessment. Enklast möjliga lösning som bevarar PADL-data utan extra resurser. Alternativet Observation nämns i profilen.

Kända begränsningar

Följande begränsningar i FHIR R4 påverkar mappningarna i denna implementationsguide. Vilka som löses i R5 framgår av Val av FHIR-version.

  1. Observation.bodySite är 0..1 (ej 0..*) — begränsar mappning av targetSite när flera anatomiska platser anges i källdata (se OBS-004). Beslutat: extension additionalBodySite används för ytterligare platser; tas bort vid R5-migration.
  2. DiagnosticReport saknar inbyggt stöd för act-poster med multimedia — fält som actCode, actText och actResult med multimediainnehåll från GetReferralOutcome har ingen direkt motsvarighet (se REF-001). Workaround: DiagnosticReport.presentedForm och extension.
  3. MedicationStatement saknar modellering av receptkedja (chain) — relationen mellan insättning (I) och utsättning (U) kan inte uttryckas med standardelement (se MED-002). Kräver extension.
  4. DocumentReference.content[0].attachment.data är base64 — stora dokument bör refereras via URL i attachment.url för att undvika onödigt stora FHIR-resurser.
  5. ImagingStudy är komplex och kan vara overkill för enbart utlåtandemetadata — för GetImagingOutcome med begränsad DICOM-referensdata kan ImagingStudy-resursen bli onödigt komplex (se IMG-002).
  6. Observation.value[x] stödjer variabelprecisions-datum dåligt — FHIR R4 dateTime kräver specifik precisionsnivå, men RIVTA-tidsstämplar kan ha varierande precision (se OBS-001). Beslutat: valueString för YYYY/YYYYMM, valueDateTime för YYYYMMDD/YYYYMMDDHHMMSS.
  7. Inga standardiserade FHIR-element för samtycke/Sparr-information — approvedForPatient-flaggan i RIVTA-headrar har ingen direkt FHIR-motsvarighet. Beslutat: meta.security med kod NOPATIENT (v3-ActCode) om false (se PDL-001).
  8. Flag saknar note-element i R4 — alertInformationComment kan inte mappas till standardelement på Flag (se ALERT-005). Kräver custom extension.
  9. AuditEvent.patient är R4B-tillägg — i R4 anges patienten med BALP:s entity-mönster (entity.role = 1), se Auditloggning och LOG-001.
  10. Logiska modeller och RIV-TA-XML — de logiska modellerna avbildar svarsmeddelandena exakt (namn, nästling, namnrymder, RIV-TA-datatyper, textinnehåll) och kan läsas av en FML-motor, se Logiska modeller. Kvarvarande begränsningar: SOAP-kuvertet måste skalas av före transformering, xs:any-utökningar ignoreras, XOR-villkor (t.ex. läkemedelsval) uttrycks bara i text, och TKB-regler för datatypernas underelement i ett visst sammanhang (t.ex. validityTimePeriod.start 1..1) står i definitionen men är inte maskinellt uttryckta.
